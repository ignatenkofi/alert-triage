# alert-triage — архитектура и требования (design stage)

Зафиксировано 2026-07-12 по обсуждению с владельцем; исходный разбор —
feedback-relay#17. Разработка — после пилота feedback-relay M2.

## 1. Задача и позиция

Homelab + пачка сервисов + один человек без on-call-ротации: alert fatigue
максимальна, времени на разбор минимум. 90% алертов — флапы и известные
грабли; их должен отсеивать агент с доступом к метрикам и истории, а не
человек в 2 часа ночи.

**Что строим:** триаж-слой поверх Alertmanager.
**Чего НЕ строим:** свой алертинг (дедуп/resolve/silences/inhibition —
Alertmanager), свою AIOps-платформу, автономного агента с руками в проде.

## 2. Архитектура

```
Prometheus → Alertmanager ──webhook_config──▶ адаптер (CF Worker или
                                              event_type=alert_v1 в воркере
                                              feedback-relay — решить в A1)
                                                      │ chat.postMessage + metadata
                                                      ▼
                                              Slack #alerts (карантин)
                                                      │ pull-свип
                                                      ▼
GitHub issue в репо проекта  ◀────────────  Claude Routine:
(+ ✅/🚫/❓-реакции, дедуп                    • диагностика через MCP
 по fingerprint/permalink)                    (PromQL «что было час назад»,
                                              активные алерты, история)
                                              • «инцидент или флап»
                                              • группировка связанных
```

Протокол триажа — реюз `feedback-relay/triage/ROUTINE.md`: та же машина
состояний в реакциях, тот же принцип «спорное — ❓ и сводка владельцу»,
формат issue адаптируется под алерты (fingerprint, ссылки на Grafana,
firing/resolved-таймлайн).

**Куда падает issue (решение владельца 2026-07-31, #5).** Alert-issue с
payload'ом всегда создаётся в **приватном** alerts-репо — независимо от того,
публичный целевой репо проекта или нет. В публичный пер-проектный репо, если
он вообще нужен, идёт только ссылка на приватный issue, без лейблов,
хостнеймов и Grafana-URL. Обоснование — проверяемость границы: полноту
редакции подтвердить нельзя (Alertmanager в любой момент приносит новый
лейбл, которого нет в фильтре), а границу репозитория — можно, она бинарна и
видна глазами. Та же политика распространяется на диагностические выводы A3:
вывод PromQL несёт адреса ровно так же, как payload. Приватный репо заводится
на A2 вместе с маппингом `alert → репо`.

## 3. Ландшафт (проверено 2026-07: не велосипед ли?)

| Решение | Что даёт | Почему не берём как есть |
|---|---|---|
| PagerDuty AIOps, incident.io, Datadog Bits AI, BigPanda | AI-группировка, разбор инцидентов | enterprise SaaS, не self-hosted, не тот масштаб |
| [Keep](https://github.com/keephq/keep) | open-source alert management + AI-корреляция | риск «слишком платформа» для нескольких VM — проверить в A0 |
| [HolmesGPT](https://github.com/robusta-dev/holmesgpt) (Robusta) | open-source AI root-cause агент по алертам | K8s-центричен (у нас Proxmox+VM) — забрать идеи промптов диагностики, проверить в A0 |

**Ниша**: карантин-канал → LLM-триаж → issues в пер-проектные репо,
human-in-the-loop через реакции, personal/homelab-масштаб — готового нет;
рынок целит в enterprise on-call. Новизна проекта — воркфлоу-слой, не
AI-диагностика.

## 4. MCP-роли (важный разрез)

- **Диагностическая рука агента = MCP, берём готовое:** официальный
  [mcp-grafana](https://github.com/grafana/mcp-grafana) (дашборды,
  datasources, alerting) + коммьюнити Prometheus/Alertmanager MCP.
  Не строить своё.
- **Транспорт алертов ≠ MCP:** MCP — pull-протокол «агент спрашивает»,
  алерт — push-событие. Доставка — webhook-адаптер; Routine подхватывает
  pull-свипом по расписанию (та же механика, что свип фидбека).
- **Протокол триажа как typed-MCP-тулзы** — см. feedback-relay#16: если
  появится, обслужит оба потока (`feedback_v1` / `alert_v1`).

## 5. Ограничение среды

Homelab (Prometheus/Alertmanager/Grafana в приватной RFC1918-подсети,
условно `192.168.X.0/24`) за Tailscale:

- диагностический MCP достижим из **локальных** Cowork-сессий (Tailscale на
  хосте) сразу;
- из облачных CCR-сессий — только через funnel/публичный endpoint с auth.

→ где живёт триаж-Routine (локально vs облако) — решение этапа A1; влияет
на расписание и на то, что доступно агенту при разборе.

Публичный репо: адреса/имена хостов homelab в конфиги не коммитим — только
примеры с плейсхолдерами (та же дисциплина, что в feedback-relay).

## 5a. Формат вебхука Alertmanager и гранулярность (вход A1, #6)

Дизайн выше говорит «алерт», а `webhook_config` присылает **группу**. Разница
не косметическая: от неё зависят единица триажа, ключ дедупа и то, к чему
вообще прикрепляются реакции. Ниже — факты формата и предлагаемое решение;
выбор фиксируется в A1, до кода адаптера.

### Что приходит на самом деле

Один POST — одна нотификация группы
([docs/configuration.md](https://github.com/prometheus/alertmanager/blob/main/docs/configuration.md),
`webhook_config`):

```json
{
  "version": "4",
  "groupKey": "<string>",
  "truncatedAlerts": "<int>",
  "status": "<resolved|firing>",
  "receiver": "<string>",
  "groupLabels": "<object>",
  "commonLabels": "<object>",
  "commonAnnotations": "<object>",
  "externalURL": "<string>",
  "notification_reason": "<string>",
  "alerts": [
    {
      "status": "<resolved|firing>",
      "labels": "<object>",
      "annotations": "<object>",
      "startsAt": "<rfc3339>",
      "endsAt": "<rfc3339>",
      "generatorURL": "<string>",
      "fingerprint": "<string>"
    }
  ]
}
```

Что из этого важно для триажа:

- **`fingerprint` — у каждого элемента `alerts[]`, а не у нотификации.** Группа
  из N алертов несёт N идентичностей.
- **`status` есть на двух уровнях.** Верхний — производный: `firing`, если
  горит хоть один. Группа бывает смешанной (часть firing, часть resolved).
- **`groupKey` стабилен, состав группы — нет.** Ключ выводится из маршрута и
  значений `group_by`; алерты внутри группы приходят и уходят, ключ остаётся
  тем же. Это единственное стабильное «имя» повторяющейся нотификации.
- **Повторная доставка — целиком.** По умолчанию `group_wait: 30s`,
  `group_interval: 5m`, `repeat_interval: 4h`: горящая группа приезжает снова
  и снова, каждый раз со всем составом.
- **`truncatedAlerts > 0` означает неполный payload.** При `max_alerts` (по
  умолчанию 0 — не резать) часть алертов в сообщение не попадает. Триаж по
  обрезанной группе — решение по неполным данным, и это обязано быть видно, а
  не подразумеваться.

### Предлагаемая гранулярность: сообщение = группа

| вариант | за | против |
|---|---|---|
| **на группу** | совпадает с единицей нотификации Alertmanager; `group_by` уже настроен так, чтобы бандлить то, что разбирают вместе; один разбор — одна реакция | смешанную группу нельзя разметить поалертно |
| на алерт (fan-out) | реакция = один fingerprint, дедуп тривиален | группа из 20 алертов даёт 20 сообщений — ровно та усталость, ради снижения которой проект и затевался, только перенесённая в Slack |
| гибрид (группа + тред на алерт) | обе гранулярности | больше механики, а спрос на поалертный разбор пока гипотетический |

**Рекомендация — на группу**, с fingerprint'ами в metadata. Основание: единица
решения здесь — «инцидент или флап», и она почти всегда про группу целиком,
потому что `group_by` для того и настраивают. Поалертную разметку добавлять
тогда, когда появится реальный случай, где она нужна, — не раньше.

**Ключ дедупа — `groupKey`**, не набор fingerprint'ов: набор меняется при
входе-выходе алертов, ключ — нет. Набор fingerprint'ов при этом хранится и
служит для другого — обнаружения смены состава.

### Черновик схемы `alert_v1.event_payload`

Аналог `{project, sdk}` из `feedback_v1`:

```jsonc
{
  "schema": "alert_v1",
  "group_key": "<groupKey — идентичность для дедупа>",
  "receiver": "<receiver>",
  "status": "firing|resolved",          // верхнеуровневый, производный
  "severity": "<из commonLabels/groupLabels, иначе максимум по alerts[]>",
  "truncated_alerts": 0,                 // >0 — payload неполный, показать явно
  "delivery": {
    "seq": 1,                            // счётчик доставок этой группы
    "first_seen": "<rfc3339>",
    "notification_reason": "<как прислал Alertmanager>"
  },
  "target": { "repo": "<приватный alerts-репо>", "rule": "<как решён маппинг>" },
  "alerts": [
    { "fingerprint": "<...>", "status": "firing|resolved",
      "starts_at": "<rfc3339>", "ends_at": "<rfc3339>" }
  ]
}
```

Полные `labels`/`annotations` в metadata **не кладём**: у Slack есть предел
размера metadata, а группа в десятки алертов с полным набором лейблов в него
не влезет. Metadata несёт идентичность и статусы (маленькое и машинное),
человекочитаемый payload живёт в теле сообщения. Точный лимит проверить перед
кодом адаптера. Куда именно уезжает payload дальше — §2: всегда приватный
alerts-репо.

### Семантика повторной доставки

Повтор той же группы — не новое событие, и новым сообщением быть не должен:
иначе `repeat_interval: 4h` сам по себе становится источником шума, а
уже принятое решение ✅/🚫 теряется вместе со старым сообщением.

| что пришло | что делает адаптер |
|---|---|
| новый `groupKey` | новое сообщение в `#alerts` |
| тот же `groupKey`, состав и статусы не изменились | нового сообщения нет; счётчик доставок и «горит с ...» обновляются в существующем |
| тот же `groupKey`, изменился состав или статусы | ответ в тред к исходному сообщению с дельтой; якорем триажа остаётся родительское сообщение |
| верхний `status: resolved` | ответ в тред о восстановлении; сообщение-якорь не дублируется |

Из этого следует ответ и на recovery-вопрос §7 (resolved — реакция или
отдельное сообщение): предлагается **тред к исходному**, одним механизмом с
остальными повторами. Пункт оставлен открытым — это решение владельца, здесь
только следствие выбранной гранулярности.

Состояние «эта группа уже разобрана» переживает повторы только если у адаптера
есть память между доставками — это #7, и он решается в A2 вместе с
ROUTINE.md. До тех пор повторы будут порождать сообщения.
